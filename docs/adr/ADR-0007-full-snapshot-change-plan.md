# ADR-0007: قرارداد Snapshot کامل و برنامه تغییر قطعی منبع

- Status: Accepted
- Date: 2026-08-30
- Work Package: Phase 1 — WP-04
- Decision owner: Codex Project Manager under Roadmap O-46/O-49

## Context

پس از تثبیت قرارداد ستون‌های Raw در WP-02 و Canonical/Hash در WP-03، مرحله بعد باید یک Snapshot کامل از چهار شیت را با آخرین وضعیت شناخته‌شده مقایسه کند و بدون وابستگی به ترتیب شیت یا ردیف، نتیجه دقیق `insert`، `edit`، `void` یا `unchanged` بسازد. خطای اصلی این مرز، تبدیل یک ورودی ناقص یا شیت جامانده به حذف گروهی معتبر است.

Roadmap حذف را فقط پس از Snapshot کامل و معتبر مجاز می‌داند، UUID را هویت دائمی رکورد می‌شناسد و Import یکسان را بدون رویداد تازه می‌خواهد. در عین حال، WP-04 هنوز Parser اکسل، قواعد الزامی هر نوع تراکنش، SQLite و Commit عملیاتی را نمی‌سازد؛ بنابراین باید «اعتبار قرارداد منبع» را به‌صورت تایپ‌شده از «اجازه Commit نهایی Import» جدا کند.

## Constraints

- Snapshot جاری باید دقیقاً هر چهار شیت ثبت‌شده در `raw-source-contract.v1` را یک‌بار داشته باشد؛ مجموعه ناقص یا دارای شیت اضافه هرگز مبنای `void` نیست.
- هر ردیف جاری باید UUIDv7 معتبر، نگاشت دقیق فیلدهای Raw همان شیت و `source_hash` بازتولیدشده با ADR-0006 داشته باشد.
- UUID در کل Workbook فضای نام یکتا دارد و شیت نخستین ثبت، خانه دائمی آن است؛ انتقال همان UUID به شیت دیگر تغییر نوع رکورد نیست.
- آخرین وضعیت شناخته‌شده باید هویت‌های Active و Voided را نگه دارد تا Retry پس از حذف، Insert کاذب نسازد و بازگشت همان هویت قابل تشخیص باشد.
- شماره ردیف، موقعیت سلول، ترتیب شیت/ردیف، Formula، Cached Value و ستون مشتق در تصمیم تغییر نقشی ندارند.
- خروجی این مرحله پیشنهاد قطعی تغییر در حافظه است، نه مجوز Commit. اعتبارسنجی‌های الزامی بعدی، تراکنش SQLite، `import_id` و Outbox در بسته‌های بعدی‌اند.
- این تصمیم هیچ مجوزی برای خواندن، کپی یا تغییر Excel مرجع/کپی واقعی، استفاده از داده واقعی یا ساخت/تغییر دیتابیس نمی‌دهد.

## Options considered

### Option A — Snapshot تایپ‌شده کامل و برنامه‌ریز خالص با رجیستری هویت

- Benefits: حذف کاذب ناشی از ورودی ناقص را در API دشوار می‌کند؛ نتیجه مستقل از ترتیب و قابل Property Test است؛ Active/Void/بازگشت هویت و Revision بعدی را صریح نگه می‌دارد؛ Persistence بعدی فقط یک Plan قطعی مصرف می‌کند.
- Costs/risks: یک مدل میانی و چند ناوردای بیشتر دارد؛ کامل‌بودن قرارداد منبع به‌تنهایی هنوز جای اعتبارسنجی کسب‌وکار و Commit اتمیک را نمی‌گیرد.
- Reversibility: بالا؛ API نسخه‌دار است و هنوز داده عملیاتی تحت آن ذخیره نشده است.

### Option B — Diff مستقیم Mappingها با فلگ `is_complete=True`

- Benefits: کد اولیه کوتاه‌تر است.
- Costs/risks: یک Boolean اشتباه می‌تواند نبود شیت یا Parse ناقص را به حذف معتبر تبدیل کند؛ نگهداری قواعد هویت، Revision و خطا میان مصرف‌کننده‌ها تکرار می‌شود.
- Reversibility: متوسط؛ پس از اتصال به Persistence، حذف این قرارداد دشوارتر می‌شود.

### Option C — مقایسه مستقیم داخل Repository/SQLite

- Benefits: تعداد DTOهای میانی کمتر و دسترسی مستقیم به وضعیت قبلی است.
- Costs/risks: منطق تصمیم به دیتابیس و ترتیب Query گره می‌خورد، آزمون خالص Windows/Linux دشوار می‌شود و مرز Atomic Commit با طبقه‌بندی تغییر مخلوط می‌گردد.
- Reversibility: پایین تا متوسط.

## Decision

Option A انتخاب شد و قرارداد عمومی نسخه 1 با ثابت `source-change-plan.v1` ساخته می‌شود.

### Snapshot جاری

- ورودی ساخت Snapshot، مجموعه شیت‌هاست؛ تابع Validator باید دقیقاً چهار نام رجیستری WP-02 را یک‌بار بپذیرد و Missing/Unknown/Duplicate Sheet را با خطای تایپ‌شده رد کند.
- هر ردیف فقط `stable_id` و Mapping دقیق Raw همان شیت دارد. Builder شناسه را به UUIDv7 lowercase استاندارد تبدیل، از Mapping کپی دفاعی تهیه و `source_hash` را با تابع WP-03 بازتولید می‌کند؛ Hash ادعاییِ قابل‌اعتماد از Caller پذیرفته نمی‌شود.
- خروجی `ValidatedSourceWorkbookSnapshot` عمیقاً تغییرناپذیر است، Hash و تعداد هر چهار شیت را دارد و تنها مسیر عمومی ساخت آن Validator است. این نوع فقط اعتبار کامل قرارداد منبع در این مرحله را اثبات می‌کند؛ تا عبور اعتبارسنجی ضروری ردیف/کسب‌وکار و تراکنش بسته بعدی، قابل Commit نیست.
- UUID در سراسر چهار شیت یکتا است، نه فقط داخل یک شیت. تکرار همان UUID در دو ردیف یا دو شیت خطای سراسری Snapshot است.

### وضعیت قبلی هویت

وضعیت قبلی یک مجموعه عمیقاً تغییرناپذیر از همه UUIDهای شناخته‌شده است و برای هر مورد حداقل این اطلاعات را دارد:

- UUIDv7 Canonical؛
- `home_sheet` تغییرناپذیر؛
- شماره آخرین Revision به‌صورت عدد صحیح مثبت؛
- Lifecycle برابر `active` یا `voided`؛
- `source_hash` فعال فقط برای وضعیت Active.

هویت Active باید Hash معتبر داشته باشد و هویت Voided نباید Hash فعال داشته باشد. UUID تکراری، Revision نامعتبر، شیت ناشناخته یا ترکیب Lifecycle/Hash ناسازگار کل وضعیت قبلی را نامعتبر می‌کند.

### قواعد Change Plan

برای هر UUID، نتیجه دقیقاً یکی از این حالت‌هاست:

| وضعیت قبلی | وضعیت جاری در همان Home Sheet | عمل | Revision برنامه‌ریزی‌شده |
|---|---|---|---:|
| ناشناخته | موجود | `insert` | `1` |
| Active با Hash یکسان | موجود | `unchanged` | بدون Revision تازه |
| Active با Hash متفاوت | موجود | `edit` | قبلی + 1 |
| Active | غایب از Snapshot کامل | `void` | قبلی + 1 |
| Voided | غایب | بدون آیتم تازه | بدون Revision تازه |
| Voided | دوباره موجود | `edit` با انتقال Lifecycle به Active | قبلی + 1 |

بازگشت یک UUID ابطال‌شده در همان شیت، ساخت هویت تازه نیست؛ Revision تازه همان رویداد و در شمارش Import یک `edit` است. حضور UUID شناخته‌شده در شیتی غیر از `home_sheet` خطای `identity relocation` و باعث رد کل Plan است. تغییر نوع رکورد باید با UUID تازه انجام شود.

هر آیتم Plan، عمل، شیت، UUID، Lifecycle/Revision/Hash قبل و ردیف Canonical جاری یا نبود آن را صریح نگه می‌دارد. `void` یک Tombstone Revision جدید است و داده Revisionهای پیشین را حذف یا بازنویسی نمی‌کند. `unchanged` برای گزارش شمارش حضور دارد ولی Revision/Event تازه تولید نمی‌کند. هویت‌های Voided که همچنان غایب‌اند در شمارش جاری وارد نمی‌شوند.

Plan و آیتم‌ها ابتدا با ترتیب قطعی شیت رجیستری و سپس bytes UUIDv7 مرتب می‌شوند. ترتیب ورودی Mapping، شیت، ردیف یا وضعیت قبلی نباید خروجی یا شمارش را عوض کند. الگوریتم باید با Index مبتنی بر UUID و حداکثر هزینه `O(n log n)` ناشی از مرتب‌سازی و حافظه `O(n)` پیاده شود؛ اسکن تو‌در‌توی کل مجموعه مجاز نیست.

## Consequences and trade-offs

- هیچ API عمومی از Booleanهایی مانند `allow_void` یا `is_complete` برای مجازکردن حذف استفاده نمی‌کند؛ Snapshot معتبر یک نوع مستقل است.
- یک Workbook ناقص، شیت جامانده یا UUID مبهم پیش از ساخت Plan رد می‌شود و بنابراین نمی‌تواند `void` گروهی بسازد.
- Sort و نمایش معادل Canonical عدد/تاریخ صفر Revision می‌سازند، ولی تفاوت واقعی Raw که ADR-0006 در Hash حفظ می‌کند `edit` است.
- بازگشت ردیف حذف‌شده با همان UUID قابل ممیزی و به‌صورت Revision همان هویت است؛ کپی یا انتقال UUID به نوع شیت دیگر پذیرفته نمی‌شود.
- Planner به‌عمد `import_id`، زمان، موقعیت سلول، دامنه مالی، Outbox و عملیات ذخیره ندارد؛ این جداسازی، تکرارپذیری تصمیم را از شکست I/O مستقل نگه می‌دارد.

## Roadmap and acceptance impact

- مرجع: بخش‌های 4.2، 4.3، 5.1، مراحل 3 تا 5 بخش 5.2 و معیارهای 19.1؛ O-03، O-06، O-07، O-26، O-31، O-58، O-68 و O-69.
- WP-04 قرارداد Snapshot و Change Plan را می‌سازد و شاهد مقایسه UUID/Hash برای Insert/Edit/Void/Sort/No-op است، اما به‌تنهایی G1 را نمی‌بندد.
- Parser/فعال‌بودن ردیف/Requiredness، فایل Snapshot روی دیسک، SQLite، Commit اتمیک، `import_id`، Outbox و گزارش Import همچنان بسته‌های بعدی‌اند.

## Evidence plan

- جدول انتقال کامل برای نخستین Import، No-op، Edit، Void، بازگشت از Void و حذف همه ردیف‌های یک شیت حاضر ولی خالی.
- رد Snapshot ناقص/اضافی/تکراری، UUID تکراری سراسری، انتقال UUID میان شیت‌ها و وضعیت قبلی ناسازگار.
- Property Test برای بی‌اثری هر جایگشت شیت‌ها، ردیف‌ها و وضعیت قبلی و حساسیت تغییر یک Hash.
- اثبات Deep Immutability و Defensive Copy برای Mappingهای ورودی و مجموعه‌های خروجی.
- اثبات Revisionهای 1 و `n+1`، شمارش دقیق چهار عمل، Hash شیت مطابق WP-03 و صفر رویداد تازه در Retry منطقی.
- ثبت Benchmark ساختگی برای حدود اندازه فعلی بدون استفاده از فایل یا داده واقعی و بازبینی نبود الگوریتم درجه دو.

## Migration and rollback impact

هنوز Schema یا داده عملیاتی تحت این قرارداد وجود ندارد، بنابراین Migration داده‌ای ندارد. تغییر معنی Transition، فضای نام UUID، ترتیب Plan یا قواعد Revision پس از مصرف عملیاتی به نسخه تازه قرارداد و Migration/Rebuild شاهددار نیاز دارد. Rollback WP-04 با حذف ماژول و مصرف‌کننده‌های هنوز منتشرنشده ممکن است؛ Revision ذخیره‌شده در آینده نباید با تغییر خاموش قرارداد بازتفسیر شود.

## Reconsideration triggers

- شاهد واقعی که یک UUID باید با حفظ هویت میان دو شیت جابه‌جا شود؛
- نیاز محصول به نمایش `reactivate` به‌عنوان شمارش مستقل به‌جای زیرنوع `edit`؛
- Benchmarkی که هزینه مرتب‌سازی یا نگهداری Snapshot کامل را برای حجم واقعی نامتناسب نشان دهد؛
- تغییر قرارداد Raw/Hash یا نیاز به چند Workbook عملیاتی هم‌زمان.

## Approval and protected assets

Excel مرجع/کپی واقعی، SQLite یا داده واقعی، Secret، Production، DNS و شاخه `main` در WP-04 دست‌نخورده می‌مانند.
